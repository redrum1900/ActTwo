# NPC 指标、规则与条件角色描述实施计划

> 设计依据：[NPC 指标与角色规则规格](../specs/2026-10-01-npc-indicators-and-persona-rules-design.md)。本计划由当前会话顺序实施；自动测试和构建会随任务运行，最终试玩与体验审核集中在功能完成后进行。

## Goal

以苏念为纵向样例，把 NPC 的“阶段”改为可配置指标、条件人格、规则与互动位置；AI 负责对话及语义事件建议，服务端负责条件判断、效果结算和存档。保留现有聊天流、物品、地点、日志、自动／手动存档体验。旧《雾港来信》暂由兼容路径运行，不扩展旧阶段机制。

## Architecture and stack

- TypeScript 契约：`packages/contracts` 定义配置、真实状态、只读快照和玩家视图。
- 规则与投影：`packages/engine` 负责类型化条件、原子效果、规则结算、人格／互动地点派生。
- 剧本：`packages/script` 读取拆分 JSON，规范化名称引用并做跨文件静态校验；苏念内容位于现有剧本目录。
- API／AI：`apps/api` 组织当前 NPC 快照、压缩上下文和候选事件，核验模型建议后提交状态，必要时修订回复。
- React：`apps/web` 消费动态可见指标、NPC 互动位置和公开变化；不自行判断规则。
- 测试：现有 `tests/*.test.ts`，`npm test` 与 `npm run build` 为最终回归命令。

## Global constraints

- 先为每项行为写失败测试并确认红灯，再作最小实现并确认绿灯。无 Git 仓库，不执行提交步骤；以计划勾选和测试输出作检查点。
- 存档是真实状态的唯一来源。NPC 快照是派生读模型，不可由 AI 或规则直接写；现有旧字段仅为旧剧本兼容。
- AI 只能建议当前 NPC 候选语义事件 ID 和角色回复；不能写数值、道具、位置、可见性。所有效果必须全成或全不成。
- 隐藏指标及其精确变化不能出现在玩家资料、提示、日志或普通 API 玩家视图；作者诊断与玩家视图分离。
- 不把用户此前发出的服务端密钥写入仓库、日志、测试快照或前端包。模拟 AI 测试用桩；最终线上调用只使用现有服务端环境变量。
- 旧档清理仅限精确确认的当前项目测试存档与图鉴记录。清理前只读确认 DB 路径、表和行数，创建可恢复备份；不碰账号或其他项目数据。
- 范围不包括创作者中心、登录／平台分发、图形编辑器或历史剧本全面迁移。

## Review focus

1. **规则门槛时序**：同轮两个语义事件不得因前一个加分而让后一个“事后满足”；测试操作前快照判定和仅一层自动规则。
2. **不可逆与类型安全**：`writeOnceTrue` 不可回退，数字上下界、枚举值、标签去重、预设文本和跨 NPC 引用均受校验；测试原子回滚。
3. **角色表达一致性**：命中人格完整替换基础文本、多个命中按配置顺序合并；本轮回复用旧人格，下一轮用新人格；测试线上渠道不会写成实体同处。
4. **权限与泄露**：隐藏指标可以影响条件和 AI，却不出现在普通玩家 API／游戏日志；测试揭示后只呈现当前值，不回放历史。
5. **AI 故障边界**：模型幻造、重复、无效或被拒事件不修改状态；修订只存最终回复；超时／无效结构不写聊天及自动档。

## Tasks

### 1. 建立类型化指标和真实状态

1. 在 `tests/engine.test.ts` 写失败测试：五种指标初值正确进入 NPC 状态；数字、枚举、布尔、标签集合、文本均有稳定值类型；`playerVisible` 是存档运行值而不是配置常量。
2. 运行该测试，确认失败原因是缺少新契约／初始化。
3. 在 `packages/contracts/src/index.ts` 增加判别联合 `IndicatorDefinition`、`IndicatorValue`、`NpcIndicatorState` 和新 NPC 配置字段；在引擎新游戏初始化中建立 `npcIndicators[npcId][indicatorId] = { value, playerVisible }`。旧剧本未配置指标时走原路径。
4. 运行定向测试及 `npm run build`，确认契约可由 API／React 消费；记录检查点。

### 2. 实现类型化条件与原子效果

1. 新增 `tests/npc-rules.test.ts` 红灯用例：递归 `all`／`any`／`not`，数值比较、等于／不等于、标签包含、带 `npcId` 的跨 NPC 条件，现有地点／时间／物品条件可组合。
2. 增加效果失败用例：越界值按定义处理、非法枚举／文本、`writeOnceTrue` 回退和不存在指标都不能产生部分写入；可见性、标签集合、物品变化在一次事务中生效。
3. 在 `packages/engine` 建立上下文明确的 `evaluateCondition` 与 `applyRuleEffects`；先对状态副本完整验证，再提交；未知运行引用安全拒绝并给服务端诊断，不静默落地。
4. 运行定向测试、原 `tests/engine.test.ts` 和构建，记录检查点。

### 3. 实现 NPC 规则结算器

1. 写红灯测试：只接受当前 NPC 已配置语义 ID；`candidateWhen` 与 `when` 分离；一次性、可重复、优先级／互斥组、多条兼容规则，以及拒绝原因。
2. 测试同轮所有语义规则以轮次开始状态检查；语义效果提交后只评估一层自动规则；自动规则不在同轮递归触发另一自动规则。
3. 实现语义建议核验、玩家动作规则、自动规则及诊断结果；把现有状态改动／游戏日志接入真实已提交效果，不记录 AI 幻造效果。
4. 运行定向测试与原阶段兼容测试，记录检查点。

### 4. 派生人格、互动位置和玩家视图

1. 写 `tests/npc-snapshot.test.ts` 红灯用例：零／单／多条人格命中；完整覆盖基础文本；多个文本按配置顺序合并；条件重新计算后即时变化。
2. 写位置用例：单 NPC 同时命中多个位置时取配置第一条并给作者诊断；线上入口明确携带 `channel: online`，不表示 NPC 身体在玩家家；条件消失时互动入口消失。
3. 写可见性用例：隐藏指标继续影响规则和 AI 快照，普通玩家投影不含其值及变化；显示后只显示当前值。
4. 实现 `deriveNpcSnapshot` 与公共玩家投影；更新游戏日志的公开变化筛选。运行定向测试和构建。

### 5. 加载、规范化和静态校验新 NPC 文件

1. 在 `tests/script.test.ts` 写失败用例：读取 `indicators/personas/rules/placements`；名字引用规范化；重复 ID、非法类型值、缺少 NPC／指标／物品／地点／事件引用在加载时给出带文件和路径的错误。
2. 实现双路径加载：有新文件的 NPC 用新机制，没有的保留旧剧本；新结构不再生成苏念旧阶段提示／状态。
3. 校验人格和位置条件引用、规则效果类型、AI 候选正反例及互斥组配置；运行脚本测试和构建。

### 6. 迁入苏念完整角色卡与规则

1. 先在 `tests/acceptance.test.ts` 固定苏念关键事实红灯：线上／饭店／她家三种完整人格，含原卡性格行为心理语气、知识边界与话题；普通寒暄不无条件加好感；真诚亲近可触发语义规则。
2. 将苏念旧 `stages.json`／`events.json` 的业务意图逐项映射到新文件；保留道具发现／获取／转移、地点、成就和结局条件。`affection`、`metInPerson`、`visitedHerHome` 及其他需要的指标配置为作者可读 JSON。
3. 测试达到门槛后自动标记并开放新地点，降好感不退回；线上入口只在玩家家可用；旧邀约快捷提示与旧阶段 ID 不进入苏念视图。
4. 运行加载、规则和验收测试；核对旧规则清单有对应新规则或明确删去理由，记录检查点。

### 7. 改造 AI 输入、回复与提交链路

1. 在 `tests/chat.test.ts`、`tests/ai-stream.test.ts` 写红灯测试：模型输入仅当前 NPC 派生快照、相关玩家状态、地点时间、压缩上下文、当前 NPC 候选事件摘要；不含完整条件／效果 JSON、其他 NPC 原始状态、旧阶段字段。需要角色合理知晓的知识仍应提供。
2. 写失败测试：模型只返回 `{ message, proposedEventIds }`；幻造事件、拒绝事件、不合法回复、超时与修订失败不污染存档；结算后需要修订时只保存最终回复；当前轮初稿／修订均沿用操作前人格。
3. 调整 `ai-adapter.ts`、`chat-service.ts` 和记忆压缩；服务端先核验结算再决定是否修订，保持已有 SSE 预览和最终事件协议。独立作者诊断记录提议／接受／拒绝理由，不进入玩家聊天。
4. 运行聊天、流式、错误处理及 API 测试，记录检查点。

### 8. 接好 API、React 和 NPC 离场体验

1. 写 API／验收红灯用例：资料页只显示公开动态指标；玩家发送后立即看到自己的气泡；后台最终回复及公开变化到达；NPC 离开当前互动入口后聊天关闭并回到当前地点列表。
2. 更新 API 公共视图和 React 显示逻辑，只用服务端派生位置／可见性；保留背包、道具详情、地点解锁、固定 header、游戏日志及存档入口。
3. 测试自动与手动槽位加载后派生快照一致，重新进入地点不显示已经离开的 NPC；运行相关测试与构建。

### 9. 精确清理旧测试进度并整理样例说明

1. 先只读检查当前 DB 的实际路径、表、故事 ID、存档／图鉴记录数以及依赖关系；把清理目标与备份路径记录在任务检查点。
2. 对精确数据库文件创建可恢复备份并校验备份可读；只清当前项目旧测试存档及旧图鉴记录，绝不清账号、剧本或其他项目数据。若目标边界不清，停在只读检查并请求确认。
3. 写／运行新游戏及旧槽位不可恢复的测试；更新 `README.md` 或剧本格式说明，解释新文件、条件、人格覆盖、AI 语义事件与诊断。

### 10. 最终自动验证与共同试玩审核

1. 运行 `npm test`、`npm run build`；若失败，定位并修复后重跑，不把旧失败说成通过。
2. 使用测试剧本模拟线上聊天、加分、解锁饭店、道具变化、家中人格、隐藏指标、NPC 离场、保存／读档；检查游戏日志和作者诊断与真实结算相符。
3. 在服务端已配置真实 AI 时做少量实际请求，核对结构化回复、token 日志和 SSE，不在测试输出暴露密钥；若上游 429／超时，标记外部验证受阻但继续完成本地模拟验收。
4. 给用户可打开的本地地址、改动摘要、自动验证结果与试玩关注点，等待用户最后体验审核。

## Completion boundary

只在新结构、苏念迁入、聊天／视图／存档联通、自动回归与构建通过后声明开发完成。真人对话质量和角色卡还原程度以用户最终试玩反馈为准，不用测试通过代替体验审核。
