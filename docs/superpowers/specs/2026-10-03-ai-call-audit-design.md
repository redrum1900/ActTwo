# AI 调用记录设计

日期：2026-10-03

## 目标与依赖

记录接入后每一次实际向模型服务发出的请求，供玩家查看自己的用量、superadmin 查看全站用量。覆盖正式游戏、创作者试玩、智能导入、聊天触发的后台记忆摘要，以及一次操作中的重试和备用模型调用。依赖统一账号；不尝试从缺少可靠用户 ID 的旧本地日志回填。

## 记录粒度与归属

- 每次上游 HTTP 尝试生成一条不可由普通用户修改的调用记录；同一玩家操作产生的分类、生成、修订、摘要、重试及备用模型尝试，用 `operation_id` 或 `turn_id` 关联，但不合并成一条。
- 记录账号 ID、故事 ID、正式发布版本标识或试玩 ID、来源类型（`formal`、`playtest`、`import`、`system`）、用途、实际模型名、服务商配置序号、开始时间、耗时、HTTP 状态／结果。后台摘要归属触发该聊天的账号；无玩家触发的独立系统任务才使用 `system` 且账号可空。
- 分别记录输入 token、输出 token、缓存写入 token、缓存命中 token。只使用服务商实际返回的字段；未返回时存 `NULL` 并显示“未知”，不能伪装成 0。缓存命中次数只对已知命中 token 大于 0 的调用计数，未知调用单独计数。
- 不存 API 密钥、完整请求提示词、玩家对话正文或模型回复正文。日志不承担聊天历史存储职责。失败、超时、格式错误即使无 token 数据也记录结果；重试和备用模型各自有一条。

## 采集边界和可靠性

在共享模型调用边界统一写入 MySQL 审计记录；游戏 AI 适配器和智能导入客户端都接入，不再依赖单机文件日志作为产品统计来源。流式响应完成后写最终用量；请求或响应失败时写可获取的状态与时间。审计写入失败不得令已经成功的游戏结算或导入失败，但必须产生服务器告警，并让 superadmin 知道统计可能有缺口。不可在客户端自行上报 token 作为可信用量。

## 查询与保留

- 玩家在“我的 AI 用量”查看本人逐条调用和按时间／故事汇总；可见模型、用途、试玩或正式、时间、结果、输入／输出／缓存用量，不展示估算费用，也不能按请求参数查询他人。
- superadmin 查看全站逐条记录和汇总，可按账号、故事、来源、模型、用途及时间筛选；服务端必须校验 `admin` 角色。费用若展示，只能标为按配置费率估算，不等同供应商账单。
- 逐条记录保留 180 天，之后清理；按账号、月份及必要维度的汇总长期保留。账号删除时清理或匿名化关联明细与汇总，不留下可识别个人的信息。
- 删除试玩记录时，快照和存档删除，关联的调用明细仍按 180 天规则保留，并以“试玩记录已删除”展示；其用量继续计入汇总。旧访客日志不回填。

## 验证

覆盖成功、无用量响应、部分缓存字段、超时、重试、备用模型、智能导入与后台摘要；检查一条上游请求只生成一条记录，同一操作的多次尝试不会漏记或合并。验证玩家只能查自身，superadmin 可查全部，删除试玩后历史用量仍可统计，日志写入故障不改变原业务结果，180 天清理不删除月汇总。
