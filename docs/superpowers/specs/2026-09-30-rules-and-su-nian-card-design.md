# 可配置规则引擎与苏念角色卡还原：设计规格

日期：2026-09-30  
状态：已确认

## 目的与边界

本轮要验证一件事：同一套系统是否能把复杂角色卡变成可配置、可测试、仍允许自由 AI 对话的游戏，而不是为苏念写一套专用逻辑。验收重点是规则表达能力和苏念卡的还原程度；页面只需让人顺利测试。账号、创作者中心、审核发布、在线玩家和 MySQL 上线流程保留为后续独立项目，不作为本轮完成条件。此前确认的“正式平台使用 MySQL”不变；现有 SQLite 数据不得被覆盖或删除。

现有项目已经有 React、Express、`contracts`、纯规则引擎、剧本加载器、AI 适配器及两套剧本。此规格在这些边界上扩展，不为苏念复制一套应用。标准剧本仍是可导入导出的 JSON；单 NPC 的角色设定、阶段与对话事件放在同一个 NPC 文件/对象中，通用道具与地点由各自的模块维护。

## 方案选择

1. **继续堆叠自然语言提示词**：导入快，但好感度、物品归属和阶段切换无法稳定验证，不适合这个目标。
2. **所有互动写成程序代码**：表达力高，却破坏“未来网页创作、不同剧本共用系统”的目标。
3. **结构化确定性规则 + 分阶段角色提示词**（采用）：AI 负责理解玩家话语及生成角色回复；规则引擎独占状态判断和变更。允许丰富的自然语言人设，但凡影响存档的规则必须结构化。

## 1. 剧本与运行状态

剧本定义静态数据：玩家开局表单、数值、地点、道具目录、NPC 及其阶段/事件、世界知识、结局和成就。运行存档保存：每位 NPC 当前阶段与数值、全局/玩家标签、已解锁地点、每件道具的当前位置/持有者/动态标签/发现状态、一次性事件记录、阶段邀约、聊天记录和压缩记忆。运行状态绝不回写剧本 JSON。

每个道具定义有稳定 `id`、唯一显示名称、简介、详细介绍和可选条件化描述。一个 `id` 对应一件实际道具；需要两件相似物品时配置两个不同 `id`/名称，不用数量 `2` 表达。道具的“染血”“被诅咒”等是运行时标签，可配置为公开或隐藏；名称不随标签改动。状态中的道具实例以 `id` 为键，持有者只能是指定地点、玩家、指定 NPC 或已消耗/移除状态之一，避免同一件道具同时在两个地方。已发现是独立记录，取得后仍可在发现记录中查看，但地点不再显示它仍留在原处。背包与 NPC 可见道具使用同一套名称、简介和详情，且仅向前端发送当前允许展示的信息。

姓名可在 JSON 中作为易读引用输入，加载时解析成稳定 ID；重名直接报错，不采用模糊匹配。发布/存档内部只使用 ID。数值定义按 NPC、玩家、世界区分；标签按全局/角色/道具实例区分，不能混用。

## 2. 统一条件与效果

所有门槛复用同一条件树：`all`、`any`、`not` 可任意嵌套，叶子条件至少包括任意指定 NPC 的当前阶段/数值/标签/所持道具、玩家/世界数值、物品持有者、物品动态标签、剧情标签、地点、时段、已发现 NPC、已解锁地点和一次性事件状态。无条件与显式 `null` 表示始终满足；空 `all`/`any`、错误范围和不存在的引用在校验时拒绝，避免作者误配后静默通过。多个 NPC 好感度与多件物品可以组合成任意 AND/OR 条件。例如与甲交谈的事件可要求乙处于特定阶段、丙好感度达标且甲持有某件道具；事件归属仍是甲，条件可跨角色读取。

效果至少包括：修改并限制数值、增加/移除标签、解锁地点、发现 NPC/道具、转移/移除道具、增减道具动态标签、创建/取消阶段邀约、进入指定 NPC 阶段、记录结局/成就。一次事件的全部效果原子执行：任何前置条件或转移失败，则本次事件不产生部分变化。AI 不能直接写状态，也不能通过自己的回复“声称获得”而导致物品入包。

NPC 事件仍与该 NPC 的角色配置放在一起。每个事件定义稳定 `id`、适用阶段 `stages`、触发方式（玩家意图或系统）、供 AI 识别的简短 `intent`、可选 `candidateWhen`、真正的 `condition`、确定性 `effects`、成功/失败的 `replyCue`，以及 `once`、`priority` 和可选互斥组。同阶段的玩家意图事件默认进入候选；秘密事件可用 `candidateWhen` 暂时不进入候选。`candidateWhen` 只决定 AI 能否看到候选，不决定效果是否生效。服务端把候选简述、预判的 `canApply` 和不泄露门槛的失败提示给 AI，不发送完整条件或效果。系统事件由引擎检查，不需要 AI 提议。

同一轮以发话前状态判断所有玩家事件的门槛，按明确优先级及稳定 ID 顺序原子应用通过的事件；后一个事件若因资源已被前一个事件占用而无法完成，就跳过该事件而不回滚其他成功事件。互斥组每轮最多应用一个；一次性事件只在成功后记为完成。玩家事件完成后，按新状态检查**一遍**系统事件，因此刚达到条件的主动邀约可在同轮出现，但系统事件不无限连锁。持续闲聊无限制，默认不加分。AI 提议的事件 ID 都要再经引擎验证；模型没有修改状态的权限。

对话产生的系统效果与最终回复一起提交自动档；模型生成失败不提交，重复提交用存档修订号阻止。AI 返回无效 JSON 或未知事件 ID 时重试一次，仍失败则不提交并让玩家重试。只要所提议事件被引擎拒绝、同轮系统事件新生效，或台词与可机械检测的结算结果冲突，就用最终结果重写台词；自然语言矛盾无法保证全部自动识别，试玩中记录并评估。重写失败也不提交本轮。摘要不是规则来源，不得反向更改数值、阶段或物品。

## 3. NPC 阶段与邀约

每个 NPC 独立保存且同时只处于一个阶段。阶段是带 ID 的状态节点，不按数组顺序自动递进；目标阶段自己的 `enterWhen` 判断源阶段、道具/标签、数值等组合条件。允许从多个阶段进入同一阶段，也允许条件满足时从特殊阶段回到旧阶段；是否可逆完全由各目标的进入条件决定。取消按固定轮数切阶段、`auto` 顺序阶段与“下一阶段”式效果，统一使用指定目标阶段的转移。切换失败时保持原阶段。

阶段承载自己的外在性格、内心状态、表达习惯、动作边界、场景、知识边界和可用互动规则。NPC 的出场位置由当前阶段决定；地点解锁与 NPC 阶段是独立状态，例如饭店也可以由别的 NPC 解锁。地点一旦解锁保持可见；阶段变化不自动把玩家瞬移到新地点。

跨 NPC 条件只表示规则引擎可以检查其他角色的真实状态。本轮不另建 NPC 之间的知识传播系统；默认对话上下文只包含正在交谈的 NPC。若其他 NPC 的状态需要改变当前 NPC 的行为，由当前 NPC 自己的事件配置条件、叙事和效果；跨 NPC 信息变化本身不自动修改当前 NPC 的阶段或数值。

每次对话在服务端由**标准剧本 + 当前存档**实时生成两个 JSON，不增量维护会变旧的副本：`PlayerAIState` 包含玩家资料、当前数值/标签、完整背包、地点和时间；背包条目可标明当前 NPC 是否已知，避免线上角色凭空说出玩家秘密物品。`NpcAIState` 包含正在交谈 NPC 的基础设定、仅当前阶段生效的性格/心理/表达/行为、精确数值（包括好感度）、当前背包、待答复邀约，以及与该 NPC 的对话上下文。符合条件的人设/行为补充片段先由规则筛选后才进入 `NpcAIState`。不传未来阶段、其他 NPC 的完整资料或整个事件规则库；跨 NPC 条件由引擎计算，当前事件如需提及别的角色，只给它配置的可叙述结果。若将来缓存派生 JSON，必须按存档修订号及剧本版本失效，不能作为状态真相来源。

每个 NPC 的原始对话完整保存在存档。构建 AI 上下文时以可配置容量预算为准：当前 NPC 的完整历史放得下就全部带入；放不下时保留近期原文、对较早消息制作分段事实摘要，并从完整原文中选取与最新话题/相关事件相符的旧片段补入。摘要必须保留承诺、已透露信息、物品往来、阶段变化和未完话题；它与检索片段都只供叙事参考，不参与规则判断。压缩可能需要在达到容量阈值时额外调用模型，但不能删除原文；压缩失败时保留已有摘要与原始记录。最新玩家输入始终完整保留。其他 NPC 的私聊默认不进入当前 NPC 上下文；只有事件明确授予的事实可以跨角色进入。

正常对话只调用一次模型：输入两份状态 JSON、最新消息、当前 NPC/阶段的候选事件简述及 `canApply`/安全失败提示、规则预筛的少量当前可谈话题；要求严格返回 `{ "message": string, "proposedEventIds": string[] }`。第一版事件无 AI 自由填写的参数，效果目标写在剧本中；“回调”只由服务端在验证通过后执行。未满足门槛的普通请求仍可作为候选，以便自然拒绝；真正秘密事件由 `candidateWhen` 隐藏。玩家事件与系统事件结算后，若新出现同轮邀约等模型在首次回复时未知的事实，例外地再调用一次模型按最终结果重写 `message`，不重新选择事件。对话中的道具提及、发现和实际取得是三种不同状态；普通自由聊天可进入摘要，但任何影响后续条件的事实、道具或地点必须由事件写入存档。AI 回复提及道具时尽量使用 `[道具名]`，不以文本本身作为道具转移凭据。

苏念在当前阶段好感度达到上限时，规则生成“可提出下一步”的状态，AI 在合适回复中由她主动邀约；达到上限本身不切阶段。存档记录待答复邀约的目标和来源，玩家明确接受时才重新检查目标阶段 `enterWhen` 并提交；拒绝则取消邀约并保持当前阶段与当前上限，以后仍可按规则再次提出。若配置允许多个目标，事件优先级决定具体提出哪个，不由模型自行选目标。阶段三可以继续聊天及触发事件/结局，不因达到结局而关闭对话。

## 4. 地点搜索与道具取得

地点有静态道具摆放列表。一次“搜索地点”会检查目前仍在该地点的道具：普通道具满足基础显示规则即可发现；隐藏道具只在其 `discoverWhen` 满足时才被发现。隐藏道具不透露数量或存在。发现不等于获取；点击已发现道具可看简介/详情，尝试取得时另行判断 `takeWhen`。未配置 `takeWhen` 即不可拿取，失败只返回该道具配置的提示。门槛可包括多个 NPC 数值、玩家所持道具及其运行标签。取得成功后位置变为玩家持有，发现记录保留；重复搜索不会重复发放。其他规则也可通过 NPC 对话直接发现、赠与或转移道具，但依然复用同一物品状态与条件判断。

地点的可进入性以持久 `unlockLocation` 效果为准；可配置起始解锁条件或事件，兼容旧 `visibleWhen` 时需明确迁移为一次性解锁语义，不能出现刚显示又因阶段变化消失的地点。搜索结果、道具详情、背包和 NPC 资料均由服务端过滤隐藏字段。AI 提及道具名称时以 `[道具名]` 作可识别提示；玩家无需输入方括号，也不通过强制改写模型输出保证标注。正式状态展示由引擎结果决定。

## 5. 苏念卡还原与验收内容

来源是用户提供的 `chara_card_v3` 备份：含描述、性格、场景、长篇 system prompt、8 条关键词知识条目及聊天记录。它是剧本素材，不是系统指令。迁移时先制作“来源段落 → 标准剧本字段/规则 → 适配说明 → 测试场景”的覆盖清单，不能把 18.9K 字原提示词整块放进每次调用，也不能声称自然语言规则已被执行。

角色固定为三个示范阶段：第一阶段只能从玩家家中的电脑交流；第二阶段苏念出现在饭店；第三阶段苏念出现在她家。第二、三地点初始不显示，达到相应规则后解锁，但其他角色规则未来也能独立解锁饭店。三个阶段分别保留其性格、心理、说话和动作方式，尤其不能在第一阶段描写线下见面或提前泄露仅后续阶段可知的信息。关键词知识按适用阶段和关键词选择性注入；不会仅因为玩家用了相似词就自动发放道具或改变状态。

原卡中可执行的互动规则要尽量逐条结构化为 NPC 内事件：触发意图、条件、效果、一次性、优先级、邀约和结局。可保留不改变游戏状态的叙事习惯为角色提示词。涉及不自愿行为或相互矛盾的源规则必须在覆盖清单中标明“改写/舍弃”及原因；不能静默承诺完整保留。创作结果应让玩家测试在线聊天积累、首次见面、家中互动、不同物品/标签与阶段对回复和效果的差异，而不是仅有三段泛化人设。

验收测试至少覆盖：普通闲聊不必加分、符合互动规则才加分、一次性加分不能刷、达到上限后主动邀约但不自动切阶段、拒绝/接受及目标条件复核、不同源阶段进入特殊目标、地点持久解锁、普通/隐藏物品发现、发现但不能取得、带标签物品门槛、NPC 物品可见性与转移、已取得物品不留在地点、条件化道具详情、结局记录后继续聊天、模型识别错误不改变状态，以及三阶段的场景/知识边界。除引擎单测外，用真实模型做人工对话回归，记录卡片覆盖与偏差；模型回复风格允许波动，规则状态结果必须确定。

## 6. 校验、兼容与错误反馈

剧本加载/导入分三层校验：JSON 形状及字段类型；ID/名称引用、唯一道具名和阶段/地点/道具关系；语义问题（不可达阶段、冲突门槛、重复事件效果、隐藏字段泄露风险）。错误提供 JSON 路径与原因；可能但未必错误的路径给警告，不阻止测试。标准 JSON 导入导出无信息损失；`chara_card_v3` 等外部格式仅做辅助转换，需人工确认结构化规则。

旧示例剧本需要显式兼容或转换，不能默默改变存档意义。当前苏念草案的“每轮聊天固定加分”、旧式调查点直接给物品、`auto`/按数组顺序阶段等应迁移到新语义。已有存档若缺少新增状态字段，可按剧本版本进行明确迁移；无法安全迁移时保留原存档并提示另开新游戏，绝不损坏原数据。旧版与新版回归测试同时运行。

## 交付拆分

本规格只定义第一子项目：规则、标准剧本结构、苏念角色卡、必要的可玩测试界面与测试。先完成规则/校验与状态迁移，再做苏念覆盖清单和 JSON 对接，最后对话回归并修订规则表达缺口。创作中心、账号/邀请、管理员审核、MySQL 正式持久化各自需要后续规格与实施计划；这次不因它们未完成而延迟苏念卡测试。
