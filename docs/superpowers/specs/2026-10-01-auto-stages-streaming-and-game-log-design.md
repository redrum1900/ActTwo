# 自动阶段、流式对话与游戏日志设计

## 目标与边界

玩家可以自由与 NPC 对话，不需要点击邀约或遵循通用开局引导。剧本条件决定 NPC 何时进入目标阶段；AI 只负责角色表达和提出候选对话事件，服务器负责校验、结算与存档。玩家发言立即显示，NPC 文字逐字显示。玩家可从游戏日志回看每次操作及其真实结果。此设计适用于所有剧本，苏念剧本是首个验证样例。

本次不建设创作者中心、账号系统或新剧本编辑器；不改变现有的手动存档分支语义，也不把后台 AI 请求用量日志当作游戏日志。

## 方案选择

- 阶段结算集中在服务端一次操作的末尾，而不是只在聊天或页面读取时检查。这覆盖对话、移动、等待、搜索、获取和探索；随机结果只抽一次并持久化。
- 游戏日志作为 `GameState` 的一部分随自动／手动存档保存。独立数据库流水表难以随读档回退；从聊天记录事后重建则无法可靠复原随机结果与无对话操作。
- AI 上游与浏览器下游均采用流式传输。生成中的 NPC 文字是临时稿，最终事件校验或改写可能替换它；采用第二次模型调用先决策再生成虽更稳定，但会显著增加 token 和等待时间。

## 剧本规则与阶段结算

`StageDefinition.enterWhen` 是目标阶段的进入门槛，可组合已有条件类型：当前 NPC／其他 NPC 阶段、数值、标签、持有且带标签的道具、地点、时段、事件和标记等。初始阶段由 `initialStage` 指定；其他阶段必须配置 `enterWhen`。剧本校验应提示缺少当前阶段约束、可能从自身重入或无效的阶段引用，避免在无新状态变化时反复跳转。当前阶段约束可用 `any` 表示多个来源阶段，因此特殊阶段仍可从多个阶段进入。

服务端在一次有效操作的事件／效果处理后，对每个 NPC 独立收集 `enterWhen` 为真且不是当前阶段的目标阶段；一个候选直接进入，多个候选用可注入的随机源等概率选一个。同一 NPC 一次操作最多切换一次，不在本次操作中连锁切换。选中的阶段写入同一次存档提交，之后才根据新状态刷新 NPC 可见性、地点解锁与图鉴。只读请求（当前存档、页面刷新、查看资料）不得抽随机或改变阶段。

当前剧本移除 `stageOffers`、接受／拒绝邀约入口及相应提示。旧的 `advanceNpcStage`、`transitionNpcStage` 和邀约数据仅作为导入旧剧本的兼容字段保留；苏念的阶段推进只依赖各目标阶段的 `enterWhen`，不能再由好感度上限或顺序数组暗中推进。阶段变化后，后续 AI 请求仅收到新的当前阶段人格与状态。

## 一次操作的结算与可见结果

统一结算顺序为：验证操作与存档版本 → 执行玩家动作或校验 AI 候选事件 → 应用有效事件与效果 → 为各 NPC 结算至多一次阶段变化 → 刷新地点、NPC 与道具可见状态 → 对比操作前后状态生成可见结果 → 写游戏日志及自动存档 → 返回最终视图。运行中不会改变剧本配置文件。

地点初次解锁时即时提示地点名称并写日志。道具仅在真正被发现、获得、转移或移除时提示／记录；隐藏物品只是满足可发现条件而尚未搜索到时，不提示、不写日志。相同变化在一次操作中只记录一次，已解锁地点不重复提示。已发生但对玩家仍保密的配置条件、候选事件 ID 和未发现物品不进入玩家可见文本。

结局／成就继续按现有规则记录，若本次新获得，也作为本次操作结果记录。普通操作即使没有规则变化（例如搜索无发现），仍有“做了什么、结果如何”的游戏日志；无效请求和失败的 AI 对话不产生正式日志。

## 游戏日志与存档

`GameState` 增加按发生顺序保存的 `activityLog`。每条包含稳定 ID、游戏内时间与地点、操作类型、可读摘要和相关实体／聊天消息引用；一次操作的实际事件、阶段、道具、地点等变化可作为关联结果条目。每轮成功对话都有简要记录，点开可定位到 NPC 原聊天；完整对话仍只保存在现有 `chats`，不复制进日志。日志展示的是服务器确认的结果，不直接采信 AI 草稿。

新游戏从空日志开始。手动存档复制日志，读档后自动存档被该手动档覆盖，日志随之回到相同时间线。旧存档补空日志，已有聊天和阶段原样保留；不伪造历史记录。旧 `pendingOffers` 在迁移视图中不再显示，并在下一次写入时清除。旧存档满足的新阶段条件只在下一次有效操作结算时处理，不在只读加载时突然抽签。日志不设固定条数截断；聊天压缩记忆不删除原聊天或日志。

## AI 与浏览器的流式对话

前端点发送后立即将玩家文字加入本地临时消息、清空输入框、标记“发送中”，并显示 NPC 思考状态；同时携带客户端生成的 `turnId` 和当前存档版本请求服务端。前端在同一 NPC 上防止并发发送，聊天区域滚动到最新内容；切换页面再返回不应把临时稿误认为正式存档。

服务端向兼容 Chat Completions 的上游发送 `stream: true`，解析 SSE `delta`，并通过自身的 SSE 响应传给浏览器。现有结构化输出仍包含 `message` 和候选事件 ID；服务端只把 `message` 字符串的内容作为临时文字片段发送，不泄露 JSON 控制字段、事件 ID 或其他内部数据。完整内容到齐后才校验 JSON、候选事件和规则。若触发事件或阶段变化需要改写，沿用现有按实际结算结果修订的流程；前端收到最终消息时原位替换临时气泡，不叠加第二条 NPC 消息。

正式玩家消息、NPC 最终回复、规则结果、游戏日志与自动存档只在所有必要 AI 调用成功后提交。SSE 最终事件携带权威视图、存档版本、结果提示和正式消息 ID；前端以其替换临时数据。上游若不给流式 `usage`，AI 请求日志如实记录为未知，不估造 token。格式修复、改写、摘要等内部调用也使用上游流式解析，但无需逐字透传给玩家；若它们发生在首段生成之后，界面持续显示“处理中”。

失败时保留玩家临时文字并标记“发送失败／重试”，清除未确认的 NPC 临时稿，服务器不写正式聊天、日志或存档。断线后用同一 `turnId` 重试；服务端检测已提交的 `turnId` 并返回既有结果，避免网络在提交后中断导致重复对话。存档版本冲突时先取最新状态，不盲目重发同一文本。超时与 429 沿用现有友好提示和有限重试策略。

## 界面

移除现有通用开局引导、目标卡、自动提示玩家该说什么的引导入口，以及旧邀约按钮；剧本中的可选对话提示不应作为强制目标。聊天布局沿用现有固定高度的消息区、固定顶部和底部输入区。临时玩家气泡、流式 NPC 气泡、失败重试与最终确认使用现有排版，只增必要状态标识，不另造一套视觉语言。

在游戏顶部快捷入口加入“游戏日志”抽屉。按时间倒序查看操作摘要，展开可看实际结果；对话条目可跳回对应 NPC 的聊天位置。地点、道具、阶段等即时提示来自本次提交的结构化结果，不从 AI 文本猜测。

若一次成功结算使正在对话的 NPC 不再位于玩家当前地点（阶段改变、时段或可见条件变化等），先确认该轮最终回复，再关闭聊天、提示“{NPC 名称}已离开这里”，返回当前地点的 NPC 列表。判断基于提交后的权威视图，而非 AI 文本；玩家主动切换地点或请求失败不显示“NPC 离开”。若同轮还解锁地点，离开提示与解锁提示都要可见，不能互相覆盖。游戏日志记录相应阶段／位置变化，不额外把自动关闭聊天当作玩家操作。

## 兼容与验证

保持现有自动／手动存档 API 的外部语义；新增流式聊天响应须同步更新前端调用，必要时保留旧非流式端点以避免现有测试／客户端断裂。剧本加载器应验证非初始阶段条件和引用，苏念脚本去掉邀约与通用引导后，仍能从线上、饭店、她家各阶段按配置进入。

测试至少覆盖：单／多候选阶段与可控随机、每 NPC 独立结算、一次操作至多一跳、只读不变更、隐藏物品不提前提示、地点／道具提示去重、旧存档补日志与读档分支、普通及失败操作日志、AI SSE 分片跨 JSON 边界、最终改写替换、429／超时／断线重试、相同 `turnId` 幂等、前端玩家消息即时出现及失败状态、NPC 离开后的提示与自动返回地点列表。构建和现有回归测试通过后，再用当前剧本进行一次端到端游玩验证。
