# 玩家页面独立路由设计

## 意图与范围

当前玩家端的故事目录、故事详情、开局资料、存档选择和游戏中界面都由 `App.tsx` 的本地 `screen` 状态切换。多数操作不更新地址，刷新和浏览器前进／后退不能还原所见页面。目标是让首页、故事详情、游戏中成为各自可直达、可刷新、可使用浏览器历史的页面，同时保持既有存档版本规则、登录流程和试玩隔离。

本次只重组玩家端路由与页面状态，不改变游戏规则、存档格式、发布版本机制或创作中心页面。地点、聊天、背包等继续是游戏中页面内部状态。

## 路由与页面

| 场景 | URL | 页面来源 |
| --- | --- | --- |
| 故事目录 | `/` | 最新可游玩故事列表 |
| 正式故事详情 | `/games/:id` | 最新发布的故事详情与版本 |
| 正式游戏中 | `/games/:id/play` | 该账号、该故事的当前自动档及其固定版本 |
| 试玩详情 | `/playtest/:projectId/:playtestId` | 对应试玩快照 |
| 试玩游戏中 | `/playtest/:projectId/:playtestId/play` | 对应试玩 ID 的自动档 |

旧 `/games/:id/continue` 用 `replaceState` 规范化为 `/games/:id/play`，仍沿用登录后继续的行为。创作中心、用量页等已有 URL 不纳入玩家路由。

前端继续使用现有 React 应用，但用一个集中、可测试的路由解析与导航层，根据 URL 渲染独立的目录、详情和游戏页面组件。站内导航更新浏览器历史，`popstate` 重新按 URL 选择页面并读取必要数据；URL 而非临时 `screen` 状态决定当前主页面。无需每次导航整站重载。

## 页面内状态与导航

- 故事详情页包含简介、继续、新游戏和存档入口。开局资料与存档列表作为详情页内的临时步骤；刷新详情页时回到简介，未提交的开局输入无需保留。
- 创建新游戏前仍确认覆盖自动档；创建成功后将最新发布版本写入自动档，再导航到游戏中 URL。
- 从手动存档读取时仍由现有后端将该档同步为自动档，然后导航到同一个游戏中 URL；URL 不包含手动存档位或版本。
- 游戏中点击退出或浏览器后退到详情，直接离开游戏界面，不另弹退出确认。浏览器前进或再次打开游戏中 URL 时重新读取自动档。
- 游戏中页面的地点、聊天、抽屉等继续为局部状态。刷新后默认回游戏内首页；存档中的游戏进度不变。
- 正式玩家返回目录使用 `/`；试玩玩家返回创作中心的原项目。试玩详情到试玩游戏中复用同样的路由机制，但始终调用试玩 API，不读取正式存档。

## 数据、版本和登录

故事详情始终读取最新发布版本，明确展示“最新发布版本”。游戏中始终从 `current` 端点读取自动档，展示自动档绑定的剧本版本，不自动升级旧档。试玩详情与游戏中使用试玩记录冻结的草稿快照；新建试玩仍由创作中心生成新的试玩 ID。

目录和详情可在未登录时浏览。访问正式游戏中 URL、开始新游戏、继续或读取存档时要求登录；登录成功后保留原目标 URL 和操作意图。试玩维持现有必须登录的规则。路由加载不可因登录弹窗短暂出现而误判为没有自动档。

## 缺失和失败状态

- 直达游戏中 URL 但没有自动档：回到对应详情 URL，并提示先开始新游戏；不得由读链接隐式创建或覆盖存档。试玩同理。
- 故事已删除、下架，或试玩记录已删除：展示明确的不可用页面及返回目录／创作中心入口，不静默跳转。
- 网络或服务器暂时失败：保留当前 URL，展示错误及重试入口；不把暂时故障误判为不存在。
- 游戏中发起中的请求若遇浏览器返回：不再把已离开的页面状态写回新页面。重新进入时以服务端自动档为准；路由切换不得重发“新游戏”或“读取手动档”等会改变存档的请求。

## 实现边界与验证

路由解析、规范化、历史更新与 `popstate` 监听集中处理；页面组件各自负责加载数据、显示加载／错误状态。现有游戏 UI 和 API 调用尽量迁移复用，避免重写结算逻辑。先补测试，再实施。

验证至少覆盖：目录到详情到游戏中地址变化；刷新详情和游戏中；浏览器后退／前进；旧 `/continue` 兼容；未登录直达游戏中并在登录后恢复；无自动档不创建游戏；手动档载入后自动档同步及旧版本展示；试玩只恢复本试玩 ID；删除／下架和暂时失败的不同呈现。运行完整测试与构建，并对桌面、窄屏和浏览器控制台做界面检查。
