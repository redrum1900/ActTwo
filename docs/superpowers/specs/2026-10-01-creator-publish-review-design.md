# 创作中心发布审核设计

## 目标与范围

普通作者可以独立创作故事，但不能让新内容未经审核进入玩家目录。管理员 `superadmin` 可查看待审版本、批准或附原因驳回。修改已上架故事时，旧线上版本一直可玩，直到新版本获批。第一版仅提供发布审核，不扩展到全站账号管理或多人共编。

## 当前机制与改造原则

当前 `/api/creator/projects/:id/publish` 会把作者草稿立即写入 `published_scripts`，目录马上可见。改造后，作者的动作改为「提交审核」，生成不可变的已校验剧本快照；只有管理员批准才能更新 `published_scripts`。作者可以继续编辑草稿，但不得改变正在审核的快照。同一故事同时最多一份待审申请；驳回或批准后可再次提交。

旧的直接发布路由不能继续绕过审核。现有 `published_scripts` 数据原样保留并继续上架；新增审核只作用于后续提交。内置 `content/` 剧本仍由部署者维护，不进入作者审核队列。

## 身份与权限

`creator_accounts` 增加由服务器管理的 `role`，默认 `author`。公开注册始终创建普通作者，客户端传入角色字段无效。`superadmin` 由一次性服务端命令创建；若用户名已存在则失败，不暗中提升现有账号。密码经现有 scrypt 加盐哈希保存；密码不进入源代码、文档、日志或浏览器返回值。

只有 `admin` 角色可调用审核列表、审核详情、批准和驳回接口；所有接口在服务器按会话角色校验。作者仅可查看自己故事的草稿、审核状态与驳回原因。管理员审核接口不需要以项目所有者身份访问作者草稿，因为它读取的是已提交的不可变审核快照。

## 审核数据与状态

新增 `creator_review_submissions`：提交 ID、项目 ID、作者 ID、提交的 `script_json`、内容哈希、版本、状态 `pending|approved|rejected`、提交时间、审核人、审核时间和驳回原因。数据库约束保证一个项目最多一个 `pending`，并保留历史记录以便追溯。

作者提交时，服务器读取当前配置项，执行现有完整校验，验证故事 ID，并在一个事务里保存快照；校验失败则不产生申请。提交响应返回申请 ID 和状态。若已有待审申请，返回冲突，不覆盖旧快照。

管理员批准时，在一个事务里确认申请仍待审、项目未删除、快照内容哈希与记录一致，然后将该快照写入 `published_scripts`，更新项目发布时间，标记申请为 `approved` 并记录审核人/时间。驳回时必须填写原因，标记 `rejected`，不修改当前线上版本。重复批准或驳回返回冲突，不产生第二次发布。

删除项目沿用现有下架语义；删除后的待审申请不能被批准，审核列表不展示它。已有玩家存档行和历史审核记录不删除。

## 页面与接口

作者编辑页把「发布故事」改为「提交审核」。故事列表和编辑页分别显示未发布、待审核、审核驳回、已发布，以及修改版待审时的「旧版仍在线」。驳回原因可见；校验结果继续指向配置项。提交成功不显示「已上架」。

管理员使用同一登录入口，进入独立审核工作台：待审列表展示故事、作者、版本、提交时间；详情查看提交快照的故事信息及完整 JSON，批准或填写原因驳回。页面沿用创作中心现有颜色、字体和交互样式，不把审核逻辑堆入游戏游玩组件。

接口：作者 `POST /api/creator/projects/:id/submit`；管理员 `GET /api/creator/reviews`、`GET /api/creator/reviews/:submissionId`、`POST /api/creator/reviews/:submissionId/approve`、`POST /api/creator/reviews/:submissionId/reject`。项目列表/详情包含最新审核状态及原因。旧 `/publish` 移除，绝不保留直发路径。

## 错误处理与验证

- 未登录返回 401；非管理员访问审核接口返回 403；作者访问他人项目仍返回 404。
- 草稿 JSON 不合法、引用错误、剧本 ID 不匹配时拒绝提交并反馈定位；已提交快照不随草稿修改。
- 同一项目重复提交待审返回 409；重复审核返回 409；项目删除后批准返回 409。
- 审核通过前新故事不进入目录；修改版待审/驳回时旧版仍可玩；批准后新版本进入目录。
- 现有已发布故事在迁移后保持可见。旧玩家存档不因审核状态变化而被删除；剧本哈希兼容规则仍按原机制执行。
- 测试覆盖注册不能自赋管理员、作者不能审批、不可变快照、事务原子性、旧版在线、批准/驳回/重复操作、服务端管理员创建命令，以及前端状态呈现。
