# 苏念剧本配置入门

这一版没有需要手动切换的「阶段」。你配置的是 NPC 指标、条件人格、初始位置和规则；NPC 后续位置保存在存档里，由规则移动。先看这些文件：

| 想改什么 | 文件 | 例子 |
| --- | --- | --- |
| 好感、是否见面、隐藏记录 | `content/sword-and-screen/npcs/su-nian/indicators.json` | `affection`、`metInPerson` |
| 她此刻的性格、行为、心理和说话方式 | `personas.json` | 一段通用描述，叠加线上、饭店或她家的条件描述 |
| 她开局在哪里 | `base.json` 的 `initialLocationId` | 电脑上 |
| 地点何时显示、能否进入、线上还是当面 | 剧本根目录的 `locations.json` | 电脑上 `online`，饭店 `in-person` |
| 哪句话加分、何时给道具或改变状态 | `rules.json` | `close-talk`、`meet-in-person` |

其余常用文件：`base.json` 是姓名、玩家可见的简短介绍、初始位置和初始道具；`lore.json` 是按条件和关键词提供给 AI 的背景知识。资料页使用 `base.description`、可见指标和已知道具；情境表达放在 `personas.json`。剧本根目录的 `items.json` 定义道具名称、简介、详情和初始标签；`locations.json` 同时定义地点、显示／进入门槛、交流方式、调查点和地点物品。没有 `placements.json`、`stages.json`、`profile.json` 或 `talking-points.json`。

## 先看一次完整流转

1. `indicators.json` 里 `affection` 初始为 0，`metInPerson` 初始为 `false`。
2. 玩家和苏念聊天。AI 只建议当前聊天可能命中的语义规则，例如 `close-talk`；后端复核条件，命中才给 `affection` 加 2。普通「你好」不应加分。
3. 当好感达到 30，`rules.json` 的 `meet-in-person` 自动规则把 `metInPerson` 设为 `true`。这项配置了 `writeOnceTrue`，以后不会变回 `false`。
4. 同一条规则用 `moveNpc` 把苏念移到饭店；`locations.json` 根据该指标显示「老街饭店」，并使用该地点的 `in-person` 互动方式；`personas.json` 改用饭店的人格描述。
5. 好感达到 60 后，类似规则设置 `visitedHerHome=true`，苏念家中才解锁。

指标和 NPC 当前位置是存档里的真实值。人格根据当前状态计算，不需要另存一个 `stage`。

## 1. 定义指标

在 `indicators.json` 中，每一项至少有不重复的 `id`、给作者看的 `name`、`type`、`initial` 和 `playerVisible`。例如：

```json
{
  "id": "affection", "name": "熟悉度", "type": "number",
  "initial": 0, "min": 0, "max": 100, "playerVisible": true
}
```

目前支持 `number`、`boolean`、`enum`、`tags`、`text`。`playerVisible:false` 只是玩家资料页不显示，规则与 AI 仍可使用这个值；规则可以用 `setIndicatorVisibility` 在游戏中改成显示或再次隐藏。不可逆布尔值可以设置 `"writeOnceTrue": true`。

## 2. 写一条条件

NPC 自己的文件中，`indicator` 可省略 `npcId`，默认指苏念。其他 NPC 的指标则必须写 ID：

```json
{ "indicator": { "id": "affection", "gte": 30 } }
```

`gte` 是大于等于；另有 `lte`、`eq`、`ne`。数组标签用 `has`，例如：

```json
{ "indicator": { "id": "relationshipTags", "has": "曾被表白" } }
```

多个条件可嵌套组合：

```json
{
  "all": [
    { "indicator": { "id": "affection", "gte": 60 } },
    { "indicator": { "id": "metInPerson", "eq": true } },
    { "not": { "hasItem": { "owner": "player", "item": "剑道御守" } } }
  ]
}
```

`all` 是全部满足，`any` 是至少一项满足，`not` 是取反。`hasItem` 可指定 `owner`、道具以及运行中的 `tags`；地点、时段、剧情 flag 等也能组合。跨 NPC 时写成 `{ "indicator": { "npcId": "另一个NPC的ID", "id": "trust", "gte": 40 } }`。`all`／`any` 必须包含条件，不要写空数组。

## 3. 写人格、地点与 NPC 移动

`personas.json` 可放一条 `id: "common"`、不写 `when` 的通用人格，写年龄、已公开的共同经历、长期性格底色和不变的边界。其他条目通过 `when` 写线上、饭店等**当前条件才成立**的行为、心理与语气；读取时总是先放通用段，再按文件顺序追加所有命中的条件段。不要把地点、尚未发生的事实或当前不该提供给 AI 的秘密写进通用段；苏念的剑道经历因此只写在饭店和她家的条件描述里。互斥情境尽量让条件不重叠。例：

```json
{ "id": "common", "name": "通用", "content": "苏念与你相识两年半，善用玩笑掩饰在意。" }
```

条件段：

```json
{
  "id": "restaurant", "name": "初次见面",
  "when": { "indicator": { "id": "metInPerson", "eq": true } },
  "content": "苏念第一次面对面说话会紧张，会看菜单、放慢语速……"
}
```

建议始终配置 `common`。苏念已把原 `base.json` 中重复的基础人格移入 `common`。

`base.json` 的 `initialLocationId` 只设置开局位置：

```json
{ "id": "su-nian", "name": "苏念", "initialLocationId": "电脑上" }
```

地点本身及其玩家门禁统一写在剧本根目录的 `locations.json`：

```json
{
  "id": "restaurant", "name": "老街饭店", "description": "二楼靠窗的座位。",
  "interactionMode": "in-person",
  "visibleWhen": { "indicator": { "npcId": "su-nian", "id": "metInPerson", "eq": true } },
  "spots": []
}
```

`visibleWhen` 首次满足后永久解锁地点；需要临时限制进入时再加 `enterWhen`，例如 `{ "playerField": { "id": "playStyle", "eq": "team" } }`，每次进入前重新检查。两者都可省略，表示开局可见、随时可进入。`interactionMode: "online"` 表示电脑远程聊天，并不表示苏念身体在玩家家。NPC 是否出现在某地，只看存档中的当前位置；规则的 `moveNpc` 效果负责移动：

```json
{ "type": "moveNpc", "locationId": "老街饭店" }
```

在苏念自己的规则中省略 `target`，默认移动苏念。要移动其他 NPC，可写 `"target": "npc:另一个NPC的ID"`。即使地点尚未对玩家解锁，NPC 也可以先移动过去。

## 4. 写对话规则

`semantic` 交给 AI 识别话意，但**AI 只建议规则 ID**，后端再检查 `when` 和执行 `effects`：

```json
{
  "id": "close-talk",
  "intent": "玩家真诚表达关心，普通寒暄不算",
  "trigger": "semantic",
  "positiveExamples": ["如果你紧张，我们可以慢慢来"],
  "negativeExamples": ["你好", "在吗"],
  "effects": [{ "type": "changeIndicator", "id": "affection", "by": 2 }]
}
```

需要门槛时写 `when`；`candidateWhen` 只决定这条规则**是否发给 AI 作为候选**，不是最终生效条件。比如给御守：候选可以在她家出现，但真正转移需要好感至少 75。`once:true` 表示只触发一次；不写则可重复。`priority` 越大越先处理；同一 `exclusiveGroup` 本轮只取一条，适合防止一句话叠加多份好感奖励。

`automatic` 不用 AI 识别，会在有效操作结算后由后端检查，例如好感达到 30 就设为已见面：

```json
{
  "id": "meet-in-person", "intent": "首次见面", "trigger": "automatic", "once": true,
  "when": { "indicator": { "id": "affection", "gte": 30 } },
  "effects": [{ "type": "setIndicator", "id": "metInPerson", "value": true }]
}
```

自动规则同一次结算只检查一层：上面刚把 `metInPerson` 变为 `true`，依赖它的另一条自动规则不会在**同一次**连环触发。`action` 类型目前预留给后续明确操作入口，不会由聊天触发。

## 5. 道具：发现、拿走、改变标签

先在 `items.json` 定义道具，包含唯一 `id`、尽量不重名的 `name`、`description` 和 `detail`。然后在 `locations.json` 某地点的 `items` 中放置：

```json
{
  "item": "practice-note", "hidden": true,
  "discoverWhen": { "flag": "knows-kendo" },
  "takeWhen": { "indicator": { "npcId": "su-nian", "id": "affection", "gte": 85 } },
  "blockedHint": "这本笔记对她很重要。"
}
```

`hidden:true` 表示条件不满足时搜索也发现不了；发现不等于可以拿，获取另看 `takeWhen`。道具的归属和标签在存档中变化，不会改写 `items.json`。规则可用 `transferItem` 移交，或用 `addItemTag` 标记「获准阅读」等状态，再用 `hasItem.tags` 判断。物品名称在 NPC 对话中用 `[道具名]` 提示玩家，玩家输入无需方括号。

## 修改后怎么检查

JSON 不能有注释或末尾多余逗号。修改配置后运行 `npm test` 和 `npm run build`；剧本加载测试会检查不少缺失引用、重复 ID 和类型错误。测试通过后建议从**新游戏**体验，因为修改存档相关配置应同步提高 `manifest.json` 的 `version`，旧版本存档不会自动迁移。真实 AI 对语义的判断还有模型误判可能；后端负责阻止不满足条件的效果，但作者仍需用实际对话检查 `intent` 和正反例是否清楚。
