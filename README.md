# ACT II

下一幕 · 用对话推进的互动故事。

在 ACT II，创作者通过网页设计世界、角色、地点和规则；玩家与角色交谈、探索地点，自己的选择会改变故事。AI 负责理解话意和生成角色回复，条件判断、道具与指标变化、存档和结局由游戏系统执行。创作者不需要手写 JSON 才能完成一个故事。

项目仍在开发中。AI 生成的内容和智能导入结果需要作者检查，试玩也可能产生真实的模型费用。

## 从网页创建故事

打开首页，登录后进入「创作中心」→「我的故事」→「新建故事」，输入名称并选择「空白故事」。新故事已经带有一个「起点」地点、一个「角色」和一段「通用」性格，可以直接修改它们，不必从零创建每项数据。故事一创建就有内部 ID；通常只需要关注显示给玩家的名称。

编辑器左侧按「剧本」「玩家」「角色」排列页面。右侧修改完成后点击底部「保存」；顶部出现「已保存」才表示服务器已收到修改。切换页面时如有未保存内容，系统会让你选择继续编辑、保存或放弃。

### 先搭好舞台

建议先到「地点」把默认「起点」改成故事开始的场景，例如「旧车站」，写下玩家能够感知的环境。交流方式选择「面对面」或「线上」。需要更多场景时点击「新增地点」；可见条件决定玩家何时看见它，进入条件决定当下能否前往。地点里的道具和调查内容可之后再补。

再到「故事设定」填写标题、副标题、列表简介、世界背景和封面，并在「开局地点」下拉框选刚保存的地点。简介是玩家挑选故事时看到的介绍；世界背景是角色对话需要遵守的环境设定。时间段可以按故事需要增加、改名或调整顺序。版本号不需要填写，审核通过时由系统生成。

「开局资料」是玩家开始新游戏前回答的问题。每项可设置标题、单行／多行文本、日期、单选或多选及默认值；新加的问题默认必填，「高级设置」里可调整「允许编辑」和「公开给角色」。只有确实需要玩家输入的信息才加问题；日期默认值留空就是留空，不会自动变成当天。

### 塑造角色和状态

在左侧「角色」下打开「基本信息」，修改默认角色的名称、简介和初始地点。角色初始地点决定开局时能否在玩家所在场景见到他／她；需要更多人物时使用「角色」旁的加号。角色可以有初始道具，道具本身应先在「道具」页面创建。

「性格行为」里的「通用」内容始终生效且不能删除：写角色稳定的性格、说话方式、边界，以及不能凭空宣布的事实。其他性格条目可设置生效条件，用于关系或剧情变化后的不同表现。「世界书」放角色知道的背景资料：选择「常驻」会持续提供，选择「触发」则填写触发词；输入后按空格或回车创建标签，逗号分隔的词也会拆开。世界书帮助角色回答，但不会替代规则结算。

「剧本指标」记录全局事实，「玩家指标」记录玩家状态，「角色 → 状态指标」记录某个角色的状态。指标可选数字、是非、选项、文本、标签数组或日期，并设置初始值；玩家和角色指标还可以选择是否对玩家可见。例如「信任」适合数字，「已经见面」适合是非，「找到的线索」适合标签数组。隐藏指标仍能参与条件和规则，但不会显示精确值。标为「系统管理」的指标由平台维护，不要把它当作普通剧情变量修改。

### 让故事产生变化

「玩家规则」适合在玩家操作后检查，「角色 → 互动规则」适合在与该角色交谈时识别意图，也可配置自动检查。一个规则可以理解成：触发方式和前置条件成立 → 按顺序执行结算效果 → 写进当前存档。AI 可以判断玩家是否表达了某种意思，但不能自行发放道具、修改指标或宣布结局。

在规则表单里填写清楚的「触发名称／意图」，选择触发方式，按需设置前置条件，并添加至少一项有效效果。条件可组合为「全部满足」或「任一满足」，也能取反；它可检查开局资料、指标、道具、地点、时间段和剧情事件。比较选项跟所选数据类型对应：数字和日期可比较大小，文本可比较相等或包含，标签数组可检查是否包含某项，是非值选择「是／否」。如果使用「增减数字指标」，正数表示增加，负数表示减少。

「仅触发一次」适合初次见面、一次性奖励等；平台会记录该规则已执行，不需要为了防止重复奖励另建大量剧情事件。「编辑分组」只是给作者整理规则：每条规则选一个分组，列表顶部可多选筛选，分组不会影响玩家游戏。规则想表示可被其他条件引用的剧情事实时，再到「故事设定」添加剧情事件，并用「记录剧情事件」效果写入它；事件名称和详情不会自动展示给玩家。

「道具」负责名称、介绍、详情和图片。把已保存的道具放入某个地点，可分别设置发现与拾取条件；也可由规则给予、移除或转移。道具“发现了”和“拿到了”不是同一件事。「成就」「结局」可设置名称、描述和触发条件；勾选隐藏后，玩家满足条件前不会看到完整内容。这些页面不需要一开始全填，按故事需要逐步增加即可。

### 一个可以照着做的小故事

下面的「雨夜来信」只使用新故事自带的基础内容，不要求编辑 JSON：

1. 新建空白故事「雨夜来信」。在「地点」把「起点」改名为「旧车站」，描述雨夜的候车室并保存；回到「故事设定」选它为开局地点，填写一句简介和世界背景，保存。
2. 在「开局资料」新增「你的名字」，类型选「单行文本」并保存。新问题默认必填，进入游戏时玩家会回答它。
3. 在默认角色的「基本信息」里把名称改为「小雨」，初始地点选「旧车站」；在「性格行为 → 通用」写明她如何说话、知道什么、不知道什么，分别保存。
4. 在「角色 → 状态指标」新增数字指标「信任」，初始值设为 0，范围设为 0–100。若希望玩家看到数值，打开「玩家可见」；保存。
5. 在「角色 → 互动规则」新增「认真回应问候」，触发方式选「语义判断」，打开「仅触发一次」。在「结算效果」添加「增减数字指标」，目标选「NPC · 小雨」→「信任」，数值填 `1`，保存。这个例子没有前置门槛；是否识别为问候仍取决于模型对玩家话语的判断。
6. 点击顶部「校验配置」，按错误列表返回对应页面修正；通过后点击「试玩」→「开始新的试玩」，在新标签页体验开局和对话。发现角色说法或规则不合适，就回编辑器修改、保存，再开始一条新的试玩。

新建的空白故事本身已有有效的基本结构；上述步骤是在它之上建立一个可交谈、可观察状态变化的最小故事。要做更完整的分支，再增加地点、道具、条件、成就和结局。

### 试玩、导入与发布

每次「开始新的试玩」都会冻结**当时已保存**的草稿，生成独立试玩记录和自动存档，在新标签页打开；之后修改草稿不会改动旧试玩。抽屉里可以继续或删除旧记录，每个故事最多保留 10 条，新增时自动移除最旧记录。试玩调用真实 AI（未配置密钥时为演示对话），不会写入正式玩家存档。

「智能导入」目前只对 `superadmin` 开放。可以上传 TXT、MD、DOC、DOCX、JSON，或直接粘贴小说、角色卡、梗概。系统只请求一次导入模型；结果先展示推断和结构问题，作者确认后才替换当前故事草稿。它不会自动消除剧情矛盾，导入后仍应逐页检查、保存并试玩。

准备发布时点击「校验配置」并修正错误，再点「提交审核」。提交会冻结一份待审内容，之后继续编辑草稿也不会改变这次申请；同一故事同时只能有一份待审申请。管理员在创作中心的「审核」中批准后，玩家目录才出现新版本。审核不调用 AI 自动审稿。被驳回时作者可查看原因，修改后再提交。

玩家必须登录才能游玩。每个故事有一个自动档和五个手动档；读取手动档会把它复制为当前自动档。再次开始新游戏会覆盖自动档，但不删除手动档。新游戏总使用最新已发布版本，旧手动档继续使用保存时的版本；每次审核通过都会留下不可变的发布快照。

## 本地运行

建议使用 Node.js 24 LTS 和可连接的 MySQL 8。复制 `.env.example` 为项目根目录的 `.env`，至少填写 `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_DATABASE`、`MYSQL_USER`、`MYSQL_PASSWORD`。缺少 MySQL 配置或连接失败时服务不会启动，也不会切换到其他数据库。服务器启动时会执行所需的数据库迁移。

```bash
npm install
npm run dev
```

浏览器访问终端显示的前端地址（通常是 `http://localhost:5173`）；API 默认在 `http://localhost:3001`。开发服务默认只监听本机。首次部署可在服务器终端创建管理员：

```bash
npm run admin:create -- superadmin
```

命令会交互式读取密码，不把明文密码放入命令行或 `.env`。玩家和创作者共用账号；只有管理员能审核故事。

真实对话需填写 `AI_API_KEY`、`AI_BASE_URL`、`AI_MODEL`；不填密钥时会使用明确标记的演示回复。小说／角色卡智能导入另用 `AI_MAIN_API_KEY`、`AI_MAIN_BASE_URL`、`AI_MAIN_MODEL`。可按 `.env.example` 配置最多三组 `AI_FALLBACK_1`～`AI_FALLBACK_3` 备用接口。密钥只由后端读取，不能提交到 Git。调用模型会消耗额度；玩家在「AI 用量」可看自己的记录，`superadmin` 可看全部记录。

### 部署要点

在服务器配置好 MySQL 和模型参数后执行 `npm run build`，设置 `NODE_ENV=production` 并运行 `npm start`。生产进程同时提供前端页面和 API；用 HTTPS 反向代理将外部请求转发到它。`PORT` 可修改监听端口；反向代理与进程在同一台机器时可设置 `GAME_API_HOST=127.0.0.1`，避免直接暴露 API 端口。生产环境应配置 `MYSQL_SSL_CA` 验证数据库服务端身份，限制数据库账号权限，定期备份 MySQL 与 `data/covers` 图片，并为公开登录／注册入口加限流。

这是当前项目的最小部署方式。宝塔站点、进程管理、证书、备份和回滚的操作见 [单机部署指南](docs/deployment.md)；正式上线仍需按目标服务器环境核对路径与域名。

## 代码结构

```text
apps/web/src/creator/       创作中心页面、表单、草稿保存和工作流
apps/web/src/catalog/       玩家故事目录
apps/web/src/story-detail/  故事详情与存档入口
apps/web/src/gameplay/      正式游玩与试玩页面
apps/api/src/modules/      账号、故事、游玩、试玩、审核等 HTTP 模块
apps/api/src/infrastructure/mysql/  数据库连接、迁移与存储实现
apps/api/src/infrastructure/ai/     模型调用、备用接口与用量记录
packages/contracts/        剧本与状态的共同类型
packages/engine/           不依赖 AI 的规则结算
packages/script/           剧本加载与校验
```

普通创作以网页表单为准。编辑器中的 JSON 模式面向需要精细调整的高级作者；它是同一份故事配置的另一种视图，并非入门步骤。想了解状态、规则与存档的技术边界，可看 [系统架构](docs/architecture.md)。

运行检查：

```bash
npm test
npm run build
```

集成测试会清空独立的 MySQL 测试库内的项目数据；运行 `npm test` 前须在 `.env` 填写 `MYSQL_TEST_*`，并确认测试库名称含 `test`、与正式库不同且可以丢弃。缺少这些配置时测试会拒绝运行，不会清理正式库。
